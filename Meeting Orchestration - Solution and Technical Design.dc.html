Meeting Orchestration — Solution Design

How the Meeting Orchestration code app is built: its components, data, interfaces, AI design, controls and release path. Written so that an architecture reviewer can assess it, a security reviewer can approve it, and a team inheriting it in two years can maintain it.

1 · Purpose, scope and audience

This document is the technical counterpart to the business case (PB-CJ-MO-001). Where that document records why, this one records how. It is the reference a reviewer approves against and the artefact a future maintainer reads first.

Scope

The Meeting Orchestration code app, its Dataverse schema, its Graph and Copilot Studio interfaces, the Power Automate fulfilment flow, the client-facing booking page, and the controls surrounding all of these.

Out of scope

Changes to Dynamics 365 schema or Exchange configuration beyond what is listed as a dependency. Tenant-level identity and network architecture, which are covered by existing bank standards this design inherits.

2 · Solution overview

A single-page React application, hosted as a Power Platform code app, is the only surface the Relationship Manager touches. It holds the journey state, the review gates and the send action. Every other component is called from it or triggered by it. There is no separately provisioned service, no bespoke hosting and no external AI endpoint.

All components sit in the bank's existing Microsoft tenancy. The code app is the only component with a user interface for staff; the booking page is the only component reachable by a client.

5 · Functional specification by screen

Screens below are captured from prototype v5, which is the behavioural specification for the build. Visual treatment is not final; behaviour is.

5.1 Meeting book — Relationship Manager

A Needs attention band surfaces exceptions — most commonly a client who cannot make any offered slot. Four counters (need action, awaiting customer, confirmed, average time to confirm) double as filters. The table below is filterable by status and searchable by free text. Row click opens the meeting record.

5.2 Meeting book — Lead banker

The lead view is the same component with a widened data scope — it is not a separate application. Access is read-wide; the lead cannot send on another banker's behalf. See §9 for the role definitions this enforces.

5.3 Step 1 — Details and AI intake

Each field carries a provenance marker: AI where the value was extracted, AI · CHECK where it was inferred rather than stated. The client is resolved against Dynamics and shown as verified; where the client record carries a partner relationship, the partner is added automatically and the fact is stated on screen. The primary action is disabled until a client and a meeting type exist.

5.4 Step 2 — Availability and times

Ranking is deterministic application logic, not model output: all-parties-free outranks partial availability; a suitable room in the requested building outranks a fallback; a location that avoids client travel is preferred. Reasons are displayed so the RM can override with knowledge the system does not hold. Where no combination fits, the app offers to widen the window or relax constraints rather than returning nothing.

5.5 Step 3 — Invitation review

The body is fully editable. Tone can be changed (formal, warm, concise) and the draft regenerated; where the RM has already edited the text, regeneration requires confirmation and a redline of what would change is available. The confirmed details and the offered times are restated above the draft so the RM approves against facts rather than memory.

5.6 Client booking page

FIGURE 8   The only client-facing surface. It shows the meeting subject, the banker, the duration, the city and the approved slots — nothing else. Selection confirms instantly.

6.1 Meeting state machine

Draft → DetailsConfirmed → SlotsResolved → AwaitingClient → Confirmed, with NeedsAction reachable from AwaitingClient and Cancelled reachable from any state. Transitions are the only permitted writes to status, and each writes a TimelineEvent.

6.2 Fields read from Dynamics 365

Client identifier, display name, salutation, primary email, owning banker, partner relationship flag and partner identity, client office or preferred location. Read-only. No write-back to Dynamics is in scope for the pilot; a future increment may log the confirmed meeting against the client record.

Every long-running operation is narrated in the interface rather than hidden behind a spinner, and a slow-response notice appears once a threshold is exceeded. This is a deliberate design position: the RM should always know what the system is doing on their behalf.

8 · AI design and governance

Model use statement

The application uses a Copilot Studio agent within the bank's Microsoft tenancy to perform two bounded language tasks: reading an unstructured client request into structured fields, and drafting client-facing text from facts the application supplies. It is generative assistance, not automated decision-making.

No automated decision producing legal or similarly significant effects is taken about any individual. No client data is used to train or fine-tune any model. No AI endpoint outside the tenancy is called.

Control Implementation
Bounded capabilityThe agent exposes exactly two operations. It has no tools, no write access to any system, and no ability to send.
Human in the loopTwo mandatory gates: details confirmation and send approval. Neither can be skipped, defaulted or automated.
ProvenanceEvery AI-derived field is visibly attributed at the point of use, with a separate marker where the value was inferred rather than stated.
Data minimisationOnly the request text and the facts needed for the draft are passed. No account, portfolio, balance or advice data is sent to the agent.
Determinism where it mattersSlot ranking, partner inclusion, room fit and all state transitions are application logic. The model influences words, never outcomes.
Guardrail managementTone, topics and prohibited content are configured in Copilot Studio, versioned there, and changed without an application release. Changes are subject to the same review as any configuration change (§14).
Retention of outputsBoth the generated draft and the human-approved final text are retained against the meeting, so what the model produced and what the bank actually sent are separately evidenced.
Quality monitoringExtraction correction rate and draft edit rate are tracked during the pilot as leading indicators of drift. A sustained rise triggers guardrail review.
Graceful degradationThe full journey is completable with the agent unavailable. AI is an accelerator, not a dependency.

ClientOpen a tokenised booking page and select from the offered slots.Reach any other data or surface.

Staff authenticate with Microsoft Entra; no local accounts exist. Graph and Dynamics are called with delegated permissions so a user can never see through the application what they could not see directly. Dataverse row-level security enforces book scoping. The three duties of authoring, approving and deploying a change are held by different people; the pipeline enforces this rather than relying on convention.

11 · Records, audit and evidence

The orchestration timeline is the primary audit artefact and is visible in the product, not only in logs. Each entry records the event, the actor, whether that actor was a human, a rule, the agent or the system, the source system, and a timestamp. It is append-only; no user role can edit or delete an entry.

Question an auditor may ask Where the answer is
What was offered to this client, and by whom?CandidateSlot rows flagged offeredToClient, plus the approved Draft and its approver.
Did a human approve the wording that left the bank?Draft.approvedBy and Draft.approvedOn; generated and final text held separately.
Was the partner included by rule or by judgement?MeetingAttendee.addedBy, with the corresponding timeline event.
When did the client choose, and from where?Booking token consumption record and the selection timeline event.
Did every downstream task complete?FulfilmentTask rows with status and external reference per task.
Who could have seen this meeting?Dataverse row-level security and Entra group membership at the time, from platform audit.

12 · Security controls

  • DLP. The application runs under the bank's existing Power Platform DLP policy; the connector set is fixed and reviewed. No unclassified or third-party connector is permitted in this solution.
  • Booking tokens. High-entropy, single-use, time-limited, and stored only as a hash. A token grants sight of one meeting's offered slots and nothing else; failed and repeated attempts are recorded and rate-limited.
  • No client authentication surface. The booking page holds no credential and no session; it cannot be used to enumerate clients or meetings.
  • Least privilege. Delegated permissions throughout; application permissions only where a background flow genuinely requires them, scoped to the specific operation.
  • Secrets. None held by the application. Connections are managed by the platform; there is no key to rotate because there is no bespoke service.
  • Input handling. Pasted request text and uploaded message files are treated as untrusted input: sanitised before display and never interpreted as instructions by the application.
  • Dependency management. Front-end dependencies are pinned and scanned in the pipeline; the platform manages the rest.

14 · Environments, ALM and change control

Every change — application code, Dataverse schema, flow definition or Copilot Studio guardrail — is version-controlled, peer-reviewed and deployed through the existing pipeline. The same-day change loop promised in the business case is a consequence of this discipline, not an exception to it: speed comes from automation, not from skipping steps.

Note on agent configuration

Copilot Studio guardrails can be changed without an application release. That is an advantage, but it is also a change-control surface: agent configuration is treated as a controlled artefact, exported to source control, and changed under the same review as code. It must not become a back door around the pipeline.

15 · Observability and support

  • Journey telemetry. Step completion, abandonment point, time in each state, extraction correction rate, draft edit rate. Used to drive the weekly change loop, not to monitor individuals.
  • Operational alerts. Failed fulfilment tasks, agent timeouts above threshold, Graph throttling, token validation failures.
  • Support model. The existing Power Platform application support model. Diagnostics use metadata; access to draft content requires a separate, logged authorisation.
  • Business monitoring. The lead-banker view is the operational dashboard for the team — ageing, stuck meetings and volume are visible in the product itself.
